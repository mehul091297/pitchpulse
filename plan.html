01 Why this direction

Three things pushed this over a generic "Netflix churn" or "Titanic" project.

It's a domain you'll actually stay curious about at 11pm during Phase 4 — that matters more than it sounds, because a semester-long project dies from neglect, not from a wrong technical call. It keeps the thread back to FairSeat: that project looked at price-capped ticket resale from a venture angle, this one looks at a real football pricing market from the data side — a coherent story across your portfolio, not two unrelated projects. And it's technically wide without being shallow: a real relational data layer, statistical forecasting, and an agent pipeline that actually does something (not a chatbot bolted onto a dashboard as an afterthought) — three skills recruiters screen for separately.

The squad-recommendation idea (added below) pushes it one rung further, and that rung has a name from your own coursework: descriptive → diagnostic → predictive → prescriptive. Phases 1–2 are descriptive (what happened to prices). The anomaly flags in Phase 4 are diagnostic (why a price moved). A points-forecast model is predictive (what happens next). A squad optimizer that turns that forecast into an actual pick, inside real budget and squad-rule constraints, is prescriptive — the rung almost no student portfolio reaches, because it means the system recommends a decision, not just a number.

02 Data track — decided

There's no public dataset of real EPL ticket resale prices — no club or exchange publishes it — so "ticket market" isn't buildable on real data alone. Both tracks below sidestep that the same way: find a market inside football that is public and genuinely repriced by real money or real decisions. Going with Track A — reasoning below the cards.

Chosen

Track A — Fantasy Premier League price market

Every FPL player has a price that rises and falls through the season purely from managers buying and selling — a real, public, dynamically-repriced market with no synthetic layer needed anywhere.

  • Fully real: historical gameweek-by-gameweek prices, ownership %, transfers in/out, form
  • No gambling adjacency — the cleanest story for an academic/placement audience
  • "Price" maps directly onto demand, exactly like the original ticket-pricing idea
github.com/vaastav/Fantasy-Premier-League →

Concretely: each season's gws/merged_gw.csv has one row per player per gameweek with value (price), selected (ownership) and transfers_balance (net demand) — everything Phase 1–4 need, already time-stamped by gameweek.

Fallback, not primary

Track B — Betting-odds market

Historical EPL match data with opening and closing bookmaker odds from multiple books — odds drift ahead of kickoff is a real, money-backed repricing signal (team news, injuries, form), structurally close to how a ticket's resale price moves as an event approaches.

  • Rich time series back to 2000, fully real, no simulation
  • Sharper quant story — odds-drift and market-efficiency analytics is a recognized sports-analytics niche
  • Comes from betting data — have a one-line framing ready ("market-efficiency analytics," not tipping) for anyone who asks
kaggle.com/datasets/marcohuiii/epl-match-data-2000-2025 →

Why A over B: zero synthetic layer either way, so it came down to overhead. Track A needs no framing caveat for a placement panel, has a free live API alongside the historical archive, and the "price" metaphor maps onto the original demand-signal idea without translation. Track B stays in the plan as a fallback — worth revisiting only if the FPL data turns out too thin for a specific analysis you want to run.

Historical vs. live, and why both matter: the community archives (merged_gw.csv) stop at last season — there's no shortcut to real current-season history because it doesn't exist yet; it has to be built gameweek by gameweek as the season happens. So historical seasons train and validate the forecasting model, while the official live FPL API (src/live_ingest.py) supplies this season's actual prices for recommend_squad() to run on. Run it once now and again every gameweek — that recurring pull is the Ingest Agent's real job, not a placeholder.

03 How the pipeline works

Four stages, one trigger. The gold path is the one that makes it "agentic" rather than just automated — the analyst's findings and anomaly flags are handed to an LLM agent that writes the report, instead of a template filling in numbers.

04 Semester roadmap

Eight phases, each one a working checkpoint you could show in a stand-up. Dates assume a Sept 1 start — shift the whole block to match your actual academic calendar.

  1. 0WK 1

    Setup & framing Sep 1 – 7

    Lock the decisions that are expensive to change later.

    • Download 1–2 seasons of merged_gw.csv (Track A), eyeball the columns
    • Repo scaffold, virtual env, GitHub with a real commit history from day one
    • Write a one-paragraph problem statement and 3–4 KPIs the project will answer
  2. 1WK 2–3

    Data layer Sep 8 – 21

    Boring but load-bearing — most portfolio projects skip this and it shows.

    • Ingest raw files into SQLite; write it as a script, not a notebook cell
    • Cleaning: missing values, dtype fixes, dedup — same techniques as your Python EDA assignment
    • EDA notebook + a one-page data dictionary
  3. 2WK 4–6

    Core dashboard Sep 22 – Oct 12

    No agent yet, no forecasting yet. This checkpoint alone is a submittable BA deliverable.

    • Streamlit + Plotly: price trend per player, ownership over time, gameweek-by-gameweek view
    • Filters by team, position, gameweek range
    Milestone: shippable v0
  4. 3WK 7–9

    Agent pipeline v1 Oct 13 – Nov 2

    Wire the four boxes from the diagram above into one working run.

    • Ingest Agent + Analyst Agent + Report Agent in CrewAI, sequential process
    • One button click → one written report, end to end
  5. 4WK 10–11

    Forecasting & anomaly detection Nov 3 – 16

    The predictive layer — this is what Phase 5's optimizer will run on.

    • Points-forecast model per player (start with a rolling-form baseline before anything fancier)
    • Anomaly/spike detector on price and transfer moves, feeding the Report Agent's flags
  6. 5WK 12–13

    Squad optimizer Nov 17 – 30

    The prescriptive layer — turns a forecast into an actual recommended pick, not just a number.

    • Constrained optimizer (PuLP): best 15 within a £100m budget, squad rules, max 3 per club
    • Report Agent explains each pick against the runners-up it passed over
    Milestone: recommends a squad
  7. 6WK 14

    Polish & deploy Dec 1 – 7

    Turn a working script into something a stranger can open and understand.

    • Error handling, loading states, empty states
    • Deploy dashboard (Streamlit Community Cloud); finalize README + this architecture diagram
  8. 7WK 15+

    Portfolio packaging Dec 8 – 14

    The work is done — now make it findable and explainable.

    • 2–3 minute demo video, one-page case study
    • Resume bullets; rehearse the "walk me through your architecture" answer
    Milestone: placement-ready

05 Tech stack

Chosen for the fastest path to a working, demoable agent pipeline — not the most impressive stack on paper. Recruiter-recognized layers throughout, with one deliberate "flex" (the agent orchestration).

LayerToolWhy this one
Data storeSQLiteZero setup, still "a real database" in an interview; swap for Postgres later if you want to show that range
Analysispandas, statsmodels/Prophet, scikit-learnSame libraries you already used in the Python EDA assignment — reuse that muscle memory
OptimizationPuLPTurns a points forecast into an actual squad pick under real constraints (budget, positions, max-per-club) — "operations research," a skill almost no BA portfolio shows
Agent orchestrationCrewAIFastest to a working sequential ingest → analyze → report pipeline for a first build; role-based agents map cleanly onto the diagram above
Agent orchestration (v2, optional)LangGraphMore explicit state control and graph visualization — a stronger "advanced" signal once v1 works; worth a v2 rebuild if time allows
LLMClaude or OpenAI APIEither works for the Report Agent's narrative step; needs an API key and a small budget for calls
DashboardStreamlit + PlotlyFastest path from pandas DataFrame to an interactive, deployable UI
DeploymentStreamlit Community CloudFree, gives you a live demo link for the resume
Version controlGitHubA clean, incremental commit history is itself a portfolio signal — don't squash it all into one commit

06 What lands in your portfolio

The finished set, not just the code.

  • GitHub repo with a README that leads with the architecture diagram, not the install instructions
  • Live demo link — a deployed dashboard someone can click without asking you to run anything locally
  • 2–3 minute demo video — screen recording narrating one full agent run, start to finish
  • One-page case study — problem, approach, one number that shows impact or accuracy, one thing you'd do differently
  • Three resume bullets — the analytics, the agent pipeline, and the squad optimizer, each with a concrete number
If you ever switch to Track B later: write the one-sentence framing into your README before you write any code — "this studies market efficiency in bookmaker pricing, not betting strategy." Decide it once, state it up front, and it stops being a question anyone needs to ask you in an interview.
